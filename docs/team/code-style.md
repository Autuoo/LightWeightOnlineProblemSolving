# 代码规范

| 项目 | 内容 |
| --- | --- |
| 版本 | v1.0（2026-11-19） |
| 技术栈 | 后端 Java 17 + Spring Boot 3 + MyBatis-Plus + MySQL；前端 Vue 3 + Vite + Pinia + Axios |
| 适用范围 | 团队全部提交与合并请求 |
| 关联文档 | 团队章程、AI 使用声明 |

## 1. 通用原则

1. **可读优先**：命名表达意图，避免缩写与魔法值；复杂逻辑必须能向他人解释。
2. **小步提交**：一次提交只做一件事，便于评审与回滚。
3. **不重复造轮子**：优先复用项目已有的 DTO、异常、API 封装与样式变量。
4. **安全默认**：默认拒绝未授权访问；不记录密钥、密码、token。
5. **可验证**：新增或修改行为必须有对应验证（接口测试、页面操作或自动化测试）。

## 2. 后端 Java 规范

### 2.1 分层与包结构

```
com.example.oj
├── common        # Result、ErrorCode、BusinessException、全局异常处理
├── config        # 安全、Jackson、判题、沙箱配置
├── controller    # 仅做参数接收、鉴权信息传递、返回 Result
├── dto           # 请求/响应对象，优先使用 record
├── entity        # 数据库实体
├── mapper        # MyBatis-Plus Mapper，不写业务
├── service       # 业务编排、事务边界
├── judge         # 判题调度、沙箱、输出比对
├── security      # JWT、过滤器
└── util          # 无状态工具方法
```

- Controller 不直接访问 Mapper，不写业务分支。
- Service 负责业务规则与事务；跨表写操作使用 `@Transactional`。
- Mapper 只做数据访问，复杂 SQL 需注释说明。

### 2.2 命名

| 元素 | 规范 | 示例 |
| --- | --- | --- |
| 类 | UpperCamelCase | `SubmissionService` |
| 方法/变量 | lowerCamelCase | `replaceTestCases` |
| 常量 | UPPER_SNAKE_CASE | `MAX_OUTPUT_CHARS` |
| DTO | 名词 + Request/Response/Detail/Item | `CustomRunRequest` |
| 布尔 | is/has/can 前缀 | `compileFailed` |

禁止：拼音命名、无意义缩写（`tmp1`、`data2`）、单字母变量（循环下标除外）。

### 2.3 DTO 与校验

- 请求/响应优先使用 `record`，字段不可变。
- 使用 Jakarta Validation 注解校验，消息为面向用户的中文：
  - `@NotNull`、`@NotBlank`、`@Size`、`@Pattern`
- 长度限制必须与前端校验、数据库字段一致（如代码 65536、输入 65536）。
- 响应字段命名与前端契约保持一致，不随意改名。

### 2.4 异常与返回

- 业务异常统一抛 `BusinessException(ErrorCode, message)`，由全局异常处理器转换。
- 错误码集中在 `ErrorCode`，禁止在业务代码里硬编码数字。
- 面向用户的错误信息要说明“发生了什么 + 怎么处理”，不暴露堆栈、SQL、内部路径。
- 不吞异常：捕获后要么处理、要么记录并转换为业务异常。

### 2.5 事务与数据一致性

- 涉及多表写入（如删除题目级联清理）必须加 `@Transactional`。
- 删除/更新前先校验目标存在与权限。
- 批量删除使用 `in` 条件前检查集合非空，避免全表误删。
- 不直接在 Controller 拼接 SQL。

### 2.6 日志

- 使用 SLF4J，禁止 `System.out.println` 输出业务日志。
- 记录关键动作：提交创建、评测终态、管理操作、外部调用失败。
- 不记录密码、JWT、API Key、完整用户代码与测试点内容。
- 异常日志带上下文（ID、操作），不打印大对象。

### 2.7 注释与文档

- 公共 DTO 字段、复杂规则、非直观算法需注释或 Javadoc。
- 注释解释“为什么”，不重复代码“做了什么”。
- 接口变更同步更新 `docs/requirements` 与前端 API 封装。

### 2.8 测试

- 优先为业务规则与边界写测试：判题状态、权限、输入校验、删除级联。
- 测试数据使用参数化/数据驱动，避免用大量 if 分支区分场景。
- 测试不依赖真实外部 AI 服务；外部调用使用可控替身或跳过标记。

## 3. 前端 Vue 规范

### 3.1 组件与文件

- 统一使用 `<script setup>` + Composition API。
- 组件文件 UpperCamelCase（`ProblemDetail.vue`），工具模块 lowerCamelCase（`http.js`）。
- 页面放 `views/`，可复用组件放 `components/`，状态放 `stores/`，接口封装放 `api/`。
- 单文件组件顺序：`<template>` → `<script setup>` → `<style scoped>`。

### 3.2 状态与接口

- 服务端请求统一走 `src/api/index.js`，不在组件中直接写 Axios。
- 错误信息优先使用 `ApiError.message`，展示给用户前确认可直接阅读。
- 全局登录态、提交状态放 Pinia；页面内临时状态用 `ref`/`computed`。
- 轮询/订阅必须在卸载时清理，定时器使用模块级变量，避免污染 store。

### 3.3 模板与可访问性

- 列表渲染必须提供稳定 `:key`。
- 按钮禁用状态与 loading 文案明确，防止重复提交。
- 表单控件配 `label`/`aria-label`；错误提示使用 `role="alert"`。
- 弹窗支持 Esc 关闭、点击遮罩关闭（运行中可阻止关闭）。
- 不展示隐藏测试点内容；自定义运行明确标注“不产生提交记录”。

### 3.4 样式

- 颜色、边框、背景优先使用 `theme.css` 变量，保证深浅色主题可读。
- 不使用固定深色文字压在浅色背景上；对比度不足视为缺陷。
- 布局优先 flex/grid，避免固定像素高度造成内容裁切。
- 组件样式使用 `scoped`；需要覆盖全局主题时使用 `[data-theme="light"]` 选择器。
- 关键提示（未配置 AI、错误、测试点缺失）必须醒目，不使用过淡的颜色。

### 3.5 交互与反馈

- 所有异步操作有 loading、成功、失败三种状态。
- 删除等不可恢复操作必须二次确认，并说明影响范围。
- 空状态、错误状态、无权限状态都要有明确文案，不能出现空白区域。
- 长列表/长输出需可滚动，等宽内容使用 `--mono` 字体。

## 4. SQL 与数据库规范

- 字符集统一 `utf8mb4`，排序规则与库一致。
- 表名/字段名使用 snake_case；索引命名 `idx_表_字段`，唯一索引 `uk_表_字段`。
- 时间字段使用 `DATETIME(3)`，默认值与更新时间由数据库维护。
- 变更脚本放 `docs/sql/`，包含建表/索引/数据修复，按版本命名。
- 禁止在生产库直接执行未评审的 `DELETE`/`UPDATE`；删除题目必须走应用层事务。
- 大数据量查询必须分页，禁止无限制 `SELECT *` 返回列表接口。

## 5. Git 与协作规范

### 5.1 分支

- `main`：可演示、可部署的稳定分支，禁止直接 push。
- `feature/<模块>-<简述>`：功能分支，如 `feature/problem-history-code`。
- `fix/<模块>-<简述>`：缺陷修复。
- 分支生命周期尽量短（≤ 3 天），每日同步 `main`。

### 5.2 提交信息

格式：

```
<type>: <简述>

<可选正文：为什么这样改>
```

type：`feat`、`fix`、`docs`、`test`、`refactor`、`chore`。

示例：

```
feat: 题目管理支持删除题目

删除时级联清理测试点、逐点结果、AI 记录与提交记录。
```

- 一次提交不混合无关改动。
- 不提交 `node_modules`、`target`、`dist`、IDE 配置、密钥文件、临时调试文件。
- AI 参与时按《AI 使用声明》添加 `AI-Used` 与 `Reviewed-By`。

### 5.3 合并请求（PR）

PR 描述必须包含：

1. 背景与目标（关联 Story/用例编号）。
2. 主要改动与影响范围。
3. 验证方式与结果（命令、页面路径、测试用例）。
4. 风险与回滚方案。
5. 截图（界面改动）。

至少 1 名相关模块成员评审通过后合并；高风险模块（认证、权限、判题、删除）需 2 人评审。

## 6. 代码评审清单

- [ ] 命名清晰，分层正确，无重复代码。
- [ ] 输入校验完整，权限校验正确。
- [ ] 事务边界正确，删除/更新有条件。
- [ ] 异常有处理与用户可读提示，无空白页。
- [ ] 无密钥、密码、token、测试点内容泄露。
- [ ] 深浅色主题下文字对比度可读。
- [ ] 异步操作有 loading/成功/失败反馈，可重复点击保护。
- [ ] 提交信息与 PR 描述完整，AI 使用已披露。
- [ ] 相关文档与接口封装已同步。

## 7. 本地检查命令

```bash
# 后端：使用 JDK 17 清理编译，避免 IDE 用高版本 JDK 产物导致运行失败
cd backend
mvn -q clean compile -DskipTests

# 前端：构建校验语法与打包
cd frontend
npm run build
```

提交前至少执行与改动相关的检查；界面改动需在浏览器中实际操作验证主路径与异常路径。
